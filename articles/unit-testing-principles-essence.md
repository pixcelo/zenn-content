## はじめに

株式会社ネクスタの tetsu.k です。
生産管理SaaS「スマートF」の開発に携わっており、受注・発注・出荷・見積などのドメインを担当するチームに所属しています。

ネクスタでは、事業の拡大とともにアプリケーションが複雑になっていくなかで、より速く、より良い価値を届け続けるために、「品質」に力を入れています。

品質を支える手段の一つが、単体テストです。
いまはAIに頼めば、テストを数秒で何十本も書いてくれます。
では、テストを増やせば品質は上がるのでしょうか。

結論から言うと、大切なのはテストの数を増やすことではなく、次の2つです。

- 良いテストを書くこと
- 目の前のテストが良いテストかどうかを見分けられること

書く手間が小さくなった今、価値の無いテストも、価値のあるテストと同じ速さで増えていくからです。

私たちのチームでも、Claude Code などのAIを使ってテストを書くのが当たり前になりました。
テストを増やす速さに、その良し悪しを見分ける力が追いついていないと感じたのが、『単体テストの考え方/使い方』を読んだきっかけです。

この記事では、実装・保守していくエンジニアが、プロダクト開発の現場で単体テストの在り方をどう考えればよいのかについて、本書（ウラジミール・コリコフ著）のエッセンスを、私たちのチームで実際にあった、AIが書いたテストの落とし穴も交えて共有します。

## なぜ「良い」テストでなければならないのか

本書が示す単体テストの目的は、ソフトウェアが持続的に成長できるようにすることです。
バグを見つけることは、その手段の一つにすぎません。

テストの無いプロジェクトは、最初は速く進みます。
しかし機能が増えるにつれて、変更のたびに「どこかが壊れていないか」を人が確かめる必要が出てきて、開発の速さは落ちていきます。

良い単体テストがあれば、変更の影響をすぐに検知できます。
既存のコードを安心して直せ、壊れたことに書いた直後に気づけ、「このコードはこう振る舞うべきだ」という約束も記録として残ります。

もちろん、テストを書く手間も、設計を見直す手間もかかります。短期的には、遅く見えるかもしれません。
それでも、変更のたびに人が確かめ続けるコストは、機能が増えるほど膨らんでいきます。
品質への投資と開発の速さは、長い目で見れば対立しません。
単体テストに限らない、ソフトウェアの質と開発のスピード全般の関係は、和田卓人さんの講演「[質とスピード](https://speakerdeck.com/twada/quality-and-speed-aws-dev-day-2023-tokyo-edition)」で詳しく解説されています。
良いテストは、将来の速さへの投資です。
ただし、これは「良いテストなら」という条件つきです。

テストの判定は、火災報知器にたとえると分かりやすくなります。

![テストの判定を火災報知器にたとえた4つの場合。火事で鳴れば正しく知らせた、火事でないのに鳴れば誤報（偽陽性）、火事なのに鳴らなければ見逃し（偽陰性）、火事でなく鳴らなければ正しく黙っていた](/images/unit-testing-principles-essence/test-judgment-alarm.png)

判定が間違うのは、見逃し（偽陰性）と誤報（偽陽性）の2つです。
本書が強調するのは、後者です。

壊れていないのに赤くなるテストが続くと、開発者はテストの失敗を信じなくなり、やがて本当の不具合を知らせる失敗まで見逃します。
誤報ばかりの火災報知器が、やがて誰にも信じられなくなるのと同じです。

:::message
信頼されないテストは、無いのと同じです。
:::

本書の中で、私が特に印象に残っている言葉に「コードは資産ではなく、負債である」というものがあります。コードが増えれば、読む負担も、変更のたびに確かめる範囲も、バグが入り込む経路も増えます。

これはテストコードにも当てはまる話です。
1本のテストを足すことは、それを読み、直し、動かし続ける責任を1本分背負うことになります。

だから目指すのは、テストを増やすことではなく、少ないテストでより多くの価値を得ることです。良いテストを書き、良いテストを見分ける力は、そのために必要です。

## AIにテストを書かせると何が起きるか

AIは、渡された情報をもとにテストを書きます。
ただ、そのコードが本来どう振る舞うべきかは、実装の中ではなく、業務の要件や仕様の中にあります。
仕様を渡さずに「テストを書いて」と頼めば、AIが手がかりにできるのは目の前の実装だけです。

その結果、次のようなテストが生まれやすくなります。

| 生まれやすいテスト | 何が起きるか |
|---|---|
| 今の実装をなぞるテスト | 内部の呼び出し順まで確かめるので、中身を整理しただけで赤くなる |
| 今のバグを正しいことにしてしまうテスト | 誤った結果がそのまま期待値になり、誤りが固定される |
| 網羅率を上げるためだけのテスト | 結果をほとんど確かめていなくても、網羅率だけは上がる |

テストは十分に整備されているように見えますが、実際には検証が不十分という状態が起こり得ます。

コードが負債であることを思い出すと、この状況の危うさが分かります。
AIは、負債をこれまでにない速さで増やせる道具でもあります。書く手間がゼロになっても、維持する手間はゼロになりません。

仕様を一緒に渡せば、出てくるテストは良くなります。
それでも、出てきたテストが本当に振る舞いを守っているか、誤報を生まないかを判断するには、何が良いテストかという物差しが要ります。

そのため、テストが良いかどうかを見分けるのは、人の仕事として残ります。

## 良いテストを見分ける物差し

では、何をもって良いテストと言えるのでしょうか。本書は、良い単体テストが備えるべき性質として4つの柱を挙げています。

![良い単体テストの4つの柱（退行に対する保護、リファクタリングへの耐性、迅速なフィードバック、保守のしやすさ）が、品質とプロジェクトの持続的な成長を支えている](/images/unit-testing-principles-essence/four-pillars-quality.png)

これを、そのまま問いの形にしてみます。

| 本書の4つの柱 | 問い |
|---|---|
| 退行に対する保護 | 本体のコードを壊したら、このテストは赤くなるか |
| リファクタリングへの耐性 | 振る舞いを変えずに中身を整理しても、このテストは通り続けるか |
| 迅速なフィードバック | このテストはすぐに終わり、すぐに結果が分かるか |
| 保守のしやすさ | このテストは読めば意図が分かり、動かすための準備が少ないか |

この4つは、どれか1つでも欠けると意味がありません。
本書は、テストの価値を4つの柱の掛け算として考えます。

本体を壊しても赤くならないテストは、どれほど速く、読みやすくても、守る力がゼロなので価値もゼロです。
逆に、どんな不具合でも見つけるテストでも、中身を整理するたびに赤くなるなら、リファクタリングへの耐性がゼロなので、やはり価値はゼロです。

ただし、最初の3つ（退行に対する保護、リファクタリングへの耐性、迅速なフィードバック）は、同時に最大にはできません。身近な例で考えてみます。

| テストの例 | 退行に対する保護 | リファクタリングへの耐性 | 迅速なフィードバック |
|---|---|---|---|
| 画面を操作して最初から最後まで通すテスト（E2Eテスト） | ○ | ○ | ×（遅い） |
| 単純なプロパティの読み書きのように、壊れようのない処理を確かめるテスト | ×（守るものがない） | ○ | ○ |
| 内部でどの処理を何回呼んだかまで確かめるテスト | ○ | ×（整理しただけで赤くなる） | ○ |

どれかを伸ばすと、別のどれかが削れます。

本書の答えは、リファクタリングへの耐性は手放さない、です。
前に見た偽陽性の害が、テスト全体への信頼を失わせるからです。

そうなると、実際に調整するのは、守る範囲の広さと実行の速さのバランスです。
速く何度も回せる単体テストでは業務のルールを細かく守り、時間のかかるE2Eテストでは画面からデータまでがつながっていることを守る。
どの振る舞いを、どの種類のテストで守るかを決めること。それが、テストを設計するということです。

## レビューで気づくための兆候

前の章の物差しは、良いテストが備える性質です。
ただ、レビューのたびに本体を壊して、テストが赤くなるかを試す人はまずいません。
必要なのは、テストのコードを読んで「この形は危ない」と気づくための手がかりです。

テストをレビューするとき、AIが書いたテストを受け取るときに見るべき兆候を、本書の考え方から、誤報・見逃し・守る価値の3つに分けて挙げます。

### 誤報の兆候

- 内部の作りを確かめている。たとえば、データを取ってくるだけの処理を何回呼んだか、private なメソッドやフィールドの中身

中身を整理しただけで赤くなるテストです。

ここで分かれ目になるのが、テスト・ダブル（本物の代わりに差し込む部品。モックやスタブの総称）の使い分けです。
メール送信、外部システムへの通知、ほかのシステムからも読まれるデータベースへの書き込みのように、外へ出ていく副作用は、使う側から見える振る舞いの一部です。モックで受け止めて、送った中身まで確かめます。
一方、データを取ってくるだけの処理は、スタブで値を用意するだけにします。スタブを何回呼んだかは内部の作りなので、確かめません。

C#（xUnit と Moq）で書くと、次のようになります。

```csharp
// NG：データを取ってくるだけの処理（SELECT）を、何回呼んだか確かめている
itemRepository.Verify(r => r.Get(100), Times.Once);

// OK：ほかのシステムからも読まれるデータベースへの書き込み（INSERT）は、書いた中身まで確かめる
orderRepository.Verify(r => r.Insert(It.Is<Order>(o => o.Quantity == 216m)), Times.Once);
```

ただし本書は、自分のアプリケーションだけが使うデータベースは、モックにせず、本物のデータベースを使う統合テストで確かめることを勧めています。
そのデータベースは外の世界ではなく、アプリケーションの一部、つまり実装の詳細だからです。
モックで確かめてよいのは、書いた中身がほかのシステムからも読まれる場合です。

:::message
ここでいう統合テストは、本書の定義に従います。
本書では、1つの振る舞いを、速く、ほかのテストから隔離して確かめるものを単体テストと呼び、そのどれかを満たさないテストをすべて統合テストと呼びます。
データベースまでつなげて確かめるテストは、その代表です。画面から通すE2Eテストも、統合テストの一種です。
:::

### 見逃しの兆候

- 緑になる理由が、本体ではなく、テストが準備したスタブの返す値にある
- 何が渡されても通る書き方になっている
- 期待値が、今の実装の値や計算式を写したものになっている

本体が壊れても緑のままのテストです。
見た目はもっともらしいので、誤報より気づきにくい兆候です。

私たちのチームでも、AIが書いたテストに、実際にこの形がありました。
テストの見直しの中で気づき、直したものです。
簡略化すると、次のようなテストです。

```csharp
// NG：計算の部品をスタブに差し替え、戻り値を準備している
// 本体は別のメソッドを呼ぶので、この準備は使われず、既定値（変化なし）が返る
calculator.Setup(c => c.RoundUpToLot(216m, 18m)).Returns(216m);

var result = sut.RoundQuantities(details);

Assert.False(result.Changed);
Assert.Equal(216m, details[0].Quantity);
```

本体が実際に呼ぶのは別のメソッドで、ここで準備した戻り値は一度も使われません。
モックライブラリ（ここでは Moq）は、既定の設定では、準備していない呼び出しに対して例外を出さず、戻り値の型の既定値を返します。
本体が呼ぶメソッドは、「数量が変わったか」と「丸めた数量」をまとめた構造体を返すものでした。
その既定値は「変わっていない」を意味するので、本体は数量を書き換えず、元の216のままになります。
そのため、本体の組み立てが壊れても結果は「変わらない」になり、テストは緑のままです。

書き込みを確かめていても、「何かしら書いた」ことしか見ていなければ、どんな中身を書いても通ります。

期待値を、実装と同じ計算式で作っているテストもあります。

```csharp
// NG：実装と同じ計算式で期待値を作っている（実装が間違っていても一致する）
Assert.Equal(unitPrice * quantity * (1 - discountRate), amount);

// OK：仕様から決めた値で確かめる（1,000円×10個、1割引なら9,000円）
Assert.Equal(9000m, amount);
```

こうした形を生みにくくする設計は、次の章で見ます。

### 守る価値がない兆候

- 単純な値の受け渡しのように、壊れようのない部分だけをなぞっている

赤にも緑にも意味がなく、維持する手間だけが残るテストです。

### 網羅率とAIへの指示

網羅率は、これらの兆候を探す補助として使います。
網羅率が教えてくれるのは、そのコードがテストの実行中に通ったかどうかだけです。
結果を確かめたかどうかは、網羅率には現れません。何も確かめないテストでも、網羅率は100%になります。
網羅率は、低い場所に気づくための合図として使い、目標の数字にはしません。

兆候は、AIへの指示にも使えます。
「内部の作りではなく振る舞いを確かめること」「期待値は仕様から決めること」と伝えれば、出てくるテストは良くなります。
ただし、出てきたテストに兆候が無いかを確かめるのは、やはり人の仕事です。

兆候は、新しいテストだけでなく、今あるテストにも見つかります。
誤報を繰り返すテストや、何も確かめていないテストは、直すか、消します。
それも、テストを良くする取り組みです。

## 良いテストを書くために、設計と向き合う

良いテストが書けるかどうかは、テストの書き方だけでは決まりません。

テストの書きにくさは、設計をどこで分ければよいかを教えてくれる合図です。

![判断とデータベースの読み書きが混ざったサービスは、テスト・ダブルを並べないと確かめられず、整理するたびに赤くなりやすい。判断を切り出すと、判断は単体テストで細かく、データベースとつなぐ薄い部分は統合テストで要所だけ守れる](/images/unit-testing-principles-essence/separate-decision.png)

### 判断を切り出す

入力と結果だけで確かめるテストが書きにくいとき、多くの場合、業務の判断とデータベースへの読み書きが、1か所に混ざっています。

メソッドを「値を返すだけ（クエリ）」と「状態を変えるだけ（コマンド）」に分ける、コマンドクエリ分離という原則があります。
前の章の「取ってくるだけの処理はスタブ、外へ出ていく副作用はモック」という使い分けも、この区別です。
これとは別に、本書は、業務の判断を外とのやり取りから分けることを勧めます。
判断は、データベースを読むことも含めて外に頼らず、受け取った値だけで答えを返す形にします。
こうしておけば、入力を渡して、返ってきた値だけを確かめるテストが書けます。
本書が最も質が高いとする、出力値ベース・テストです。

たとえば、注文の数量が最小ロットに満たないとき、またはロットの倍数でないときは登録させない処理が、次のように書かれているとします。

```csharp
// NG：判断とデータベースの読み書きが、1か所に混ざっている
public void Register(OrderRequest request)
{
    var item = _itemRepository.Get(request.ItemId);   // 読む
    if (request.Quantity < item.MinLot
        || request.Quantity % item.LotSize != 0)       // 判断
    {
        throw new ValidationException("数量がロット条件を満たしていません");
    }

    _orderRepository.Insert(new Order(request));       // 書く
}
```

確かめたいのは判断だけなのに、取得や書き込みをテスト・ダブルで用意するか、実際のデータベースを用意しないと、テストが書けません。
判断を切り出すと、こうなります。

```csharp
// OK：判断を切り出す（受け取った値だけで答えを返す）
public bool Validate(decimal quantity, decimal minLot, decimal lotSize)
{
    return quantity >= minLot && quantity % lotSize == 0;
}

// 判断は、入力と結果だけで確かめられる
var validator = new OrderValidator();

Assert.False(validator.Validate(quantity: 12m, minLot: 18m, lotSize: 6m)); // ロットの倍数だが、最小ロット未満
Assert.False(validator.Validate(quantity: 20m, minLot: 18m, lotSize: 6m)); // 最小ロット以上だが、ロットの倍数でない
Assert.True(validator.Validate(quantity: 18m, minLot: 18m, lotSize: 6m));  // ちょうど最小ロット
```

元の `Register` には、読み書きと、判断の結果に従う分岐だけが残ります。

```csharp
// 薄い部分：読んで、判断に渡し、結果に従って書く
public void Register(OrderRequest request)
{
    var item = _itemRepository.Get(request.ItemId);
    if (!_validator.Validate(request.Quantity, item.MinLot, item.LotSize))
    {
        throw new ValidationException("数量がロット条件を満たしていません");
    }

    _orderRepository.Insert(new Order(request));
}
```

:::message
Validator を別のクラスに分けるだけでは、まだ半分です。
要点は、判断に必要な値を受け取る形にすることです。
クラスを分けても、その中でデータベースを読んでいれば、テストには結局スタブが要ります。
:::

切り出した判断は、スタブに差し替える必要がありません。
前の章の丸めのテストのように、確かめたいはずの判断そのものをスタブにしてしまうことも、なくなります。

読み書きの部分は、その判断のとおりに動く薄い役割に絞れます。
この薄い部分は、実際のデータベースまで通して確かめる統合テストで守ります。
統合テストは判断も含めて全体を通しますが、確かめる流れは絞ります。
統合テストは遅く、準備も重いので、数は絞り、壊れると困る流れだけを守ります。
判断は速い単体テストで細かく、データベースとのつながりは統合テストで要所だけ。
それぞれの強みに合わせて守る範囲を分けることも、前に見た「テストを設計する」ことです。

もちろん、判断の途中でデータを読み直す処理のように、きれいに分けられないこともあります。
本書も、この分離には性能や単純さとの引き換えがあると認めています。
それでも、どこまで分けるかを考えること自体が、設計を考えることです。

### 切り出すことと、中身を晒すことは違う

逆の方向にも注意が要ります。
テストを書きやすくするために、本来隠しておくべき中身を、外から触れるようにしてしまうことです。

テストが、外から見えない中身を直接のぞくのも同じです。
AIに「テストを書いて」とだけ頼むと、テストを通すためにこれを選ぶことがあります。
私たちのチームでも、AIが書いた画面のテストが、画面に何が表示されるかではなく、private なフィールドの値を読んで確かめていた例がありました。
そのテストは、画面からボタンが消えても緑のままでした。
これも見直しの中で気づき、画面の表示を確かめる形に書き直しています。

判断を切り出すことと、中身を晒すことは違います。
切り出した判断は、「この入力ならこの結果」という約束を持つ、新しい部品です。
晒した中身は、約束ではなく作りの詳細です。
作りの詳細を確かめるテストは、整理すれば赤くなり、本当に壊れても気づけないことがあります。

### テストを足場に、設計を整える

ここで、「設計の悪いコードにテストを書いても意味がない。まず設計を直すべきだ」と思った方もいるかもしれません。
もっともな意見です。
ただ、設計を直すこと自体が、安全網を必要とする作業です。
振る舞いが変わっていないことを確かめる手段が無いまま作り替えれば、それは改善ではなく賭けになります。

設計を直したいからこそ、先にテストがあります。

とはいえ、判断とデータベースへの読み書きが絡み合ったコードに、振る舞いを確かめる単体テストを書くのは簡単ではありません。
無理に単体テストにすると、モックだらけで、中身を整理するたびに赤くなるテストになりがちです。
そのときは、遅くなっても、統合テストで結果を確かめます。
前に見たとおり、リファクタリングへの耐性は手放さないからです。
作り替えの前後で通り続けられるのは、内部の作りではなく、振る舞いを確かめているテストだけです。

足場の架け方は、次の3段です。
まず、統合テストで今の振る舞いを守ります。
次に、その安全網の上で判断を切り出します。
切り出せたら、細かい確認は単体テストに移し、統合テストは要所だけを残します。

![統合テストを足場として組み、その安全網の上で判断を切り出し、細かい確認を単体テストへ移して統合テストは要所だけ残す、という3段の進め方。主役は中の設計で、テストはそれを支える足場](/images/unit-testing-principles-essence/scaffold-steps.png)

良いテストを書くとは、テストの書き方を工夫するだけでなく、確かめやすい形に設計を整えることでもあります。
良いテストを考えることと、良い設計を考えることは、同じ問いの表と裏です。

## おわりに

品質は、後から検査で足すことはできません。
テストや検査を担う人がいても、品質を作り込むのは、日々コードを書く開発者です。

AIのおかげで、テストを書く手間は大きく減りました。
だからこそ、開発者の仕事の中心に残るのは、良いテストを書くこと、そして良いテストを見分けることです。

品質に力を入れることは、テストの本数を増やすことではありません。
壊れたら知らせ、壊れていなければ黙っている。
そんな信頼できるテストを持つことです。
そしてそれは、開発を遅くするためではなく、速いまま続けるための投資です。

私たちのチームでは、ここで挙げた兆候を、テストのレビューの観点や、AIにテストを書かせるときの指示に取り入れ始めています。
この物差しと兆候を共有しながら、これからもテストと向き合っていきたいと考えています。
